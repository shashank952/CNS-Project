# Agentix Implementation Plan: Digital Signature Generation and Verification System

This plan is designed to be given directly to the Agentix coding agent. It defines the project requirements, architecture, development phases, implementation tasks, security rules, testing strategy, and completion criteria.

The agent should build a complete, working course project, not just generate a UI or a collection of code files. It should implement and test each phase before proceeding to the next.

## 1. Project definition

Project title

Digital Signature Generation and Verification System

Project type

Full-stack web application

Difficulty

Intermediate course project

Estimated duration

Approximately 7–10 development days

Primary objective

Generate digital signatures for documents and verify their authenticity and integrity using public-key cryptography.

### Problem statement

- Documents exchanged digitally can be modified without obvious visible signs.
- A recipient needs a reliable way to check whether a document matches the data originally signed.
- The application will use digital signatures to verify the integrity of a document and its relationship to a particular public-private key pair.
- The application should demonstrate the process through a simple, understandable interface.

### Project objectives

- Generate RSA public-private key pairs.
- Allow users to sign documents using a private key.
- Allow users to verify signatures using a public key.
- Detect document modifications.
- Allow users to download and reuse signature and key files.
- Maintain a basic history of signing and verification activities.
- Explain cryptographic operations through a clean dashboard.

## 3. Functional requirements

Agentix must implement the following features.

### Module A — Dashboard

- Create a home page that explains what the system does.
- Display summary cards:
  - Total signing operations.
  - Total verification attempts.
  - Successful verifications.
  - Failed verifications.
- Show recent activity with document name, operation, timestamp, and result.
- Provide navigation to the signing, verification, key management, and history pages.
- Display useful empty states when no activity exists.
- Fetch summary values from the backend instead of using hardcoded numbers.

### Module B — RSA key management

- Generate an RSA key pair using the `cryptography` library.
- Use a key size of 2048 bits.
- Export the private key in PEM format.
- Export the public key in PEM format.
- Allow the user to download both keys separately.
- Use an encrypted private-key export protected by a password where supported.
- Never expose the private key through logs, the dashboard, API responses, or the database.
- Never automatically regenerate a key when the user selects an existing key for signing or verification.
- Provide clear instructions explaining that the private key signs documents and the public key verifies signatures.

Key management design decision:

- Do not create a full account system or centralized key vault.
- Generate the keys locally on the backend for the course demonstration.
- Return downloadable key files through a controlled response.
- Keep private-key material out of persistent server storage by default.
- Allow users to provide an existing private key for signing and a public key for verification.
- If a private key is encrypted, require the corresponding password when loading it.

### Module C — Document signing

- Support PDF and TXT files.
- Accept a document upload and a private-key PEM file.
- Provide an optional password field for an encrypted private key.
- Validate the file and private key before processing.
- Read the complete original document as bytes.
- Generate a digital signature using RSA-PSS with SHA-256.
- Produce a downloadable `.sig` file.
- Display:
  - Document name.
  - Document size.
  - SHA-256 fingerprint of the document.
  - Signature algorithm.
  - Signature generation timestamp.
  - Signing result.
- Display the file download controls after successful signing.
- Record the operation in the database without storing the private key or the entire document.

### Module D — Signature verification

- Accept three inputs:
  - Original document.
  - Signature file.
  - Public-key PEM file.
- Read the original document bytes without changing them.
- Load and validate the public key.
- Verify the signature using the same RSA-PSS and SHA-256 parameters used during signing.
- Return a valid or invalid result.
- Display a clear reason or category for failure where possible:
  - Document or signature mismatch.
  - Incorrect public key.
  - Invalid signature format.
  - Invalid public-key format.
  - Missing input.
- Handle verification failure as a normal application result, not as a server crash.
- Record the result in the verification history.

Important: The application must never trust the filename, the displayed hash, or information supplied by the frontend as proof of validity. The backend must perform the actual cryptographic verification.

### Module E — Document integrity demonstration

This is an important feature for demonstrating the project during evaluation.

- Provide an optional way to edit or modify a TXT document for testing.
- Alternatively, allow the user to upload a modified copy of a previously signed file.
- Verify the modified file against the original signature.
- Display an invalid result.
- Explain that even a small change to the signed bytes invalidates the signature, except with a negligible cryptographic probability of a collision or successful forgery.

This feature can be implemented with a small demonstration panel; it does not require a separate document editor.

### Module F — Activity history

- Store signing and verification records in SQLite.
- Store only the information necessary for the activity log:
  - Record ID.
  - Document filename.
  - Operation type.
  - Timestamp.
  - Result.
  - Algorithm used.
  - Optional document SHA-256 fingerprint.
- Do not store private keys, passwords, or uploaded document contents.
- Provide a history table with sorting by most recent activity.
- Support filtering by operation type and result.
- Include a clear-history function with confirmation.
- Make the dashboard summary cards reflect the stored records.

- Perform signing and verification.

- Return signature files and key files as downloads.
- Record operation metadata in SQLite.

### Frontend responsibilities

- Validate required fields before submission.

## 6. API specification

Agentix should implement these endpoints and keep their behavior consistent.

| Method and endpoint        | Input                                        | Expected output                                                     |
| -------------------------- | -------------------------------------------- | ------------------------------------------------------------------- |
| `GET /api/health`          | None                                         | API health status                                                   |
| `POST /api/keys/generate`  | Optional key password or export option       | Public and private key downloads, or controlled download references |
| `POST /api/sign`           | Document, private key, optional key password | Signature file and signing metadata                                 |
| `POST /api/verify`         | Document, `.sig` file, public key            | Verification status and reason category                             |
| `GET /api/history`         | Optional filters                             | List of operation records                                           |
| `DELETE /api/history`      | None                                         | Confirmation of history deletion                                    |
| `GET /api/dashboard/stats` | None                                         | Summary counts and recent activity                                  |

The key-generation endpoint may return a ZIP containing the PEM files, or provide separate downloads. Choose the simplest secure implementation.

### API response conventions

For signing:

- Return a successful HTTP response only after signature generation completes.
- Include the document fingerprint, algorithm, and operation ID in response metadata.
- Return the signature as a downloadable file or a correctly encoded payload.
- Do not return the private key in the signing response.

For verification:

- Return `valid: true` for successful verification.
- Return `valid: false` for an ordinary failed verification.
- Include a machine-readable reason category and a user-friendly message.
- Use appropriate HTTP error codes for malformed requests or server failures.

For all endpoints:

- Validate required fields.
- Enforce upload-size limits.
- Use consistent response formats.
- Avoid exposing internal exceptions or sensitive file paths.

## 7. Cryptography implementation rules

This section is mandatory because incorrect cryptographic implementation could make the application appear functional while failing to provide real security.

- Use `cryptography.hazmat.primitives.asymmetric.rsa` for RSA.
- Generate a 2048-bit RSA key pair.
- Use public exponent `65537`.
- Use RSA-PSS for signatures.
- Use SHA-256 as the message digest.
- Use MGF1 with SHA-256 for RSA-PSS.
- Use `PSS.MAX_LENGTH` as the salt length, consistently in both signing and verification.
- Sign the original document bytes directly through the library's signing API.
- Do not manually implement RSA, SHA-256, padding, or signature verification.
- Do not sign the filename, file path, or a hash string displayed by the frontend instead of the actual document bytes.
- Do not use a normal RSA encryption operation as a substitute for digital signing.
- Do not compare signatures byte-for-byte to determine validity; RSA-PSS can generate different valid signatures for the same document.
- Do not treat a matching document hash alone as proof of authenticity.

### Key export

- Export private keys in PEM format using PKCS#8 serialization.
- Prefer encrypted private-key export using a password-based encryption option provided by the library.
- Export public keys in PEM SubjectPublicKeyInfo format.
- Validate imported key types and supported key sizes.
- Never log passwords or key material.
- Avoid keeping temporary key files after their purpose is complete.

## 11. Detailed testing requirements

Agentix must create automated tests and run them. It must not report tests as passed unless they have actually executed successfully.

### Cryptography tests

- Generate an RSA key pair and confirm both keys can be loaded.
- Sign a TXT document and verify the signature successfully.
- Sign a PDF and verify the original PDF successfully.
- Modify a single byte in a signed document and confirm verification fails.
- Use a different public key and confirm verification fails.
- Supply an empty signature file and confirm verification fails safely.
- Supply a malformed private key and confirm signing is rejected.
- Supply a malformed public key and confirm verification is rejected.
- Verify that signing and verification use the same RSA-PSS parameters.
- Verify that a signature remains valid after downloading and re-uploading the document, signature, and public key.

### API tests

- Test every endpoint with valid inputs.
- Test requests with missing required fields.
- Test unsupported file types and oversized files.
- Test corrupted uploads.
- Confirm that invalid verification produces a controlled response.
- Confirm that unexpected server errors do not reveal stack traces.
- Confirm that history records are saved and retrieved correctly.
- Confirm that clearing history requires the intended operation and updates dashboard statistics.

### Frontend tests

- Confirm that every navigation link opens the correct page.
- Confirm that the forms show validation errors.
- Confirm that successful signing provides a working signature download.
- Confirm that the verification page displays the backend's actual result.
- Confirm that loading, success, failure, and empty states work.
- Confirm that the history filters and clear-history confirmation work.
- Check the layout at desktop and mobile widths.

## 12. Security and implementation boundaries

Agentix must follow these constraints throughout development.

- Private-key security: Do not persist private keys on the server by default. Never put them in logs, SQLite, Git, or browser local storage.
- Key encryption: Support encrypted private-key exports using a password. Do not store the password.
- File safety: Enforce a configurable upload limit, validate file types, use safe temporary-file handling, and remove temporary files after processing.
- Cryptographic correctness: Use the `cryptography` library; do not write custom cryptographic primitives.
- Backend authority: Only the backend can determine whether a signature is valid.
- Database safety: Use parameterized queries and store only necessary metadata.
- Frontend security: Avoid unsafe HTML rendering, and do not trust user-supplied filenames or status values.
- CORS: Restrict allowed origins to the frontend during development and to the deployed frontend origin in production.
- Deployment: Disable Flask debug mode in production and use HTTPS when deployed.
- Scope control: Do not introduce authentication, user roles, digital certificates, blockchain, cloud key storage, email notifications, or third-party APIs.
- Honest reporting: Report unfinished functionality, failed tests, and known limitations instead of marking them complete.

One important limitation should be documented: this application verifies a signature against a supplied public key; it does not independently verify the real-world identity of the signer. Identity verification would require an additional trusted mechanism, such as a certificate infrastructure, which is outside the project scope.
